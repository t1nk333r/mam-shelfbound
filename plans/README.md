## Post-implementation audit (2026-07-24, branch `advisor/plans-001-012` @ `57c0af6`)

Plans 001-012 are all DONE but live on branch `advisor/plans-001-012`, **not
merged**. `master` is still `f8d3d32` with zero source drift, so re-auditing it
would only re-surface the twelve findings already fixed on that branch.

This pass therefore audited the **485 lines the implementation added** — the
torrent-client abstraction, `app/conftest.py`, the new test suite, the rewired
call sites, the CI job, `.dockerignore`. That surface had been reviewed only
*against its own plans*, never audited with fresh eyes for defects the changes
introduced. **Plans 013 and 014 target that branch, not `master`** — both stamp
`57c0af6` and their drift checks reference it.

- **013 — `pytest` can mutate a real database at collection time.**
  `app/conftest.py` uses `os.environ.setdefault("HISTORY_DB_URL", ...)`, so a
  developer with that variable already exported gets *their* database. Because
  `import main` runs `ensure_history_schema()` at module scope, and plan 012 made
  that function mutate rows, merely **collecting** the suite rewrites data.
  Demonstrated: a seeded `importing` row became `added` under
  `pytest --collect-only`, with no test body executing. This is an **emergent**
  defect — plan 001 introduced the env knob and the `setdefault`, plan 012 made
  the schema function mutating; neither is wrong alone, and per-plan review could
  not have caught it. Fix: force the assignment instead of defaulting it.

- **014 — qBittorrent add can record a NULL hash, stranding the row forever.**
  `torrents/add` returns no infohash and registers asynchronously; the follow-up
  `torrents/info` query fires with no retry, so losing the race yields `None` →
  NULL `torrent_hash` → excluded by `torrent_hash IS NOT NULL` in the candidate
  query → never imported, no Retry button. Same stranded-row class plan 012
  fixed, through a door its `importing`-only reset does not cover. A secondary,
  **lower-likelihood** issue rides along: `arr[0]` is an arbitrary pick (verified
  returning the older torrent from a two-element response), though in practice
  the same MAM id yields the same infohash and qB deduplicates, so two torrents
  rarely share a `mamid` tag. The race is the motivating defect; one change
  (retry, then pick newest by `added_on`) fixes both.

### Targeted plan request (2026-07-24) — 015

Written via `plan`, not an audit finding. Closes the coverage gap recorded twice
in this index: `QbittorrentClient`'s three real methods (`add_torrent`,
`completed_hashes`, `torrent_source`) had **zero** tests — the suite only covered
client selection and tag building.

Approach was validated before the plan was written, not assumed:

- Each qB method opens its **own** `httpx.AsyncClient`, so no fake client can be
  injected — mocking must happen at the transport layer. That is why `respx` is
  introduced (dev-only; `Dockerfile` installs `requirements.txt` alone, and
  `.dockerignore` already excludes `requirements-dev.txt` and `app/tests/`).
- `respx` 0.23.1 verified compatible with the pinned `httpx==0.28.*`, and
  `@respx.mock` verified to intercept calls made inside `asyncio.run(...)` from a
  **synchronous** test — so no `pytest-asyncio` and no pytest config are needed.
- The full 10-test module was written and run against the real client before the
  plan was finalised: 10 pass, suite goes 19 -> **29**.

**Interaction with 014**: 015's happy-path tests deliberately use single-element
`torrents/info` responses and never assert *which* element is selected, so they
survive 014's change from `arr[0]` to newest-by-`added_on`. The two plans are
independent and may land in either order; after 014, one 015 test becomes ~2s
slower because `add_torrent` retries. That is expected — production retry
defaults must not be tuned for test speed.

**Known limit, stated in the plan**: these tests encode what this code *believes*
qBittorrent's Web API v2 does. They cannot detect that belief being wrong, so a
live qB smoke test is still required before trusting qB support.

## Reconcile pass (2026-07-23, at commit `f8d3d32`)

A second `improve` run. **No source drift**: `git diff 92761c0..f8d3d32` touches
only binary image files (favicons, logo, `icon.png`, a screenshot), so every plan
above still matches live code verbatim and all excerpts remain accurate. All
plans were still `TODO` at the time of this pass. Two new findings, both
verified by reading the code:

- **`sanitize()` lets a bare `..` through** → **folded into plan 003** as Step 3
  (plus tests), rather than a separate plan: same vulnerability class, same fix
  location. `sanitize` neutralises `/` and `\` but leaves `..` untouched, so an
  author or title of exactly `..` makes the destination `/library/../Book`,
  which resolves to `/Book` — outside the library root. Author/title reach that
  code from the `/add` body and are **persisted**, so a bad value re-triggers on
  every retry. Plan 003's original scope covered only torrent-supplied file names.
- **Rows stranded in `importing`** → **planned (012)**. No code path can move a
  row out of `importing`: the poller excludes it, the retry endpoint rejects it,
  the UI renders no button, and the startup backfill only touches NULL/empty
  statuses. A process death mid-import strands it permanently and silently.
  Note `asyncio.CancelledError` is a `BaseException`, so the `except Exception`
  handlers at `app/main.py:535` and `:855` don't catch a shutdown cancellation.

### Second reconcile pass (2026-07-23, same commit `f8d3d32`)

A follow-up pass closed the gap left above: **all 11 original plans were read and
validated against live source**, not just the four checked in the first pass.

**Every plan is still valid — none stale, none already fixed.** Verified:
`requirements.txt` has zero `==` pins (002); `datetime.utcnow()` at `:92` and
`@app.on_event` at `:899`/`:903` are present, `contextlib`/`lifespan` absent
(004); no `/health` route exists but `AGENTS.md:33` still names it, and all six
route decorators match the plan's line numbers exactly (005); `.dockerignore`
does not exist (010); `payload.get("perpage", 25)` at `:210` (011);
`checked` at `index.html:181`, `: true` fallback at `app.js:36`, and the
`True if ... is None` coercion at `main.py:423` (009); 008's three
client-specific operations are where it says they are.

**One new finding — `mam_id` query injection on `/add` → folded into plan 011.**
`mam_id` is interpolated raw into the MAM download URL
(`app/main.py:437-439`) behind only a non-empty check. Because the injection
point is after the `?`, an id of `12345&fl=1` appends a real query parameter:
parsed, the URL yields `{'tid': ['12345'], 'fl': ['1']}`. Consequences: it
spends a freeleech wedge on an **ebook**, bypassing the deliberate
audiobook-only policy from commit `92c95a3`; and it flips
`used_fl = candidate_url.endswith("&fl=1")` (`app/main.py:445`), corrupting the
wedge count returned to the UI. Folded into 011 rather than given its own plan —
same class (unvalidated request field forwarded to MAM), same file, same
one-helper fix shape. 011 was raised P3 → P2 accordingly.

**Explicitly NOT SSRF.** The host stays `www.myanonamouse.net` under every probe
(`@evil.com`, `#`, `../`, spaces) because the injection lands in the query
string. Recorded here so a future audit does not re-raise it as an
outbound-request vulnerability.

**Severity is honest, not inflated**: the app has no auth by design, so anyone
able to POST `/add` could spend a wedge through the UI anyway, and browser CSRF
is blocked by the CORS preflight on `application/json`. The value is policy
integrity and correctness, not a broken security boundary.

### Negative findings from the second pass (investigated, no plan)

- **Retry TOCTOU** — `retry_history_import` reads `torrent_status`, then writes
  `importing` in a separate transaction (`app/main.py:500-528`). Two concurrent
  retries could both pass the guard. *Not worth doing*: the frontend disables the
  button on click (`app/static/app.js:252`), and the worst outcome is a duplicate
  library folder via `next_available`, not corruption.
- **Concurrent same-name import** — two imports of the same author/title could
  both resolve `next_available` to the same unused path and interleave, and a
  failure in one would `rmtree` the other's files (`app/main.py:814-817`).
  *Unreachable today*: the auto-import loop is a single sequential task, and a
  manual retry cannot overlap it (retry requires `import_failed`, which the
  candidate query excludes). Revisit if imports are ever parallelised.
- **Torrent added but `insert_history` fails** — leaves an orphan torrent with no
  history row, never imported (`app/main.py:453-459`). *Not worth doing*:
  requires a SQLite write failure at one specific instant.
- **`ensure_history_schema` ALTER TABLE race** — two processes starting at once
  could both attempt the same `ALTER TABLE`. *Not worth doing*: single-instance
  by design; already noted in plan 012's maintenance notes.
- **Command injection / unsafe deserialization** — swept and **absent**. No
  `subprocess`, `os.system`, `popen`, `shell=True`, `pickle`, `yaml.load`,
  `eval`, `exec`, or `__import__` anywhere in `app/main.py`. The only parsing of
  upstream data is `json.loads` inside `flatten` (`app/main.py:250`), which is
  safe by construction.
- **Symlink traversal in `hardlink_one`/`copy_one`** — an in-tree symlink could
  still point outward. *Already acknowledged*: plan 003 defers it explicitly in
  its maintenance notes. Not a new finding.
